# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis fits the repro evidence | The plan's stated cause, read against every step and every control run in the repro evidence (and any `--debug`/trace output it shows) | The stated cause is consistent with ALL of the repro evidence: no control run rules it out. A control the plan explicitly accounts for with a reasonable explanation passes even if that explanation is not separately proven, as long as nothing in the evidence contradicts it (whether it is stated with honest confidence is the "Unknowns" check's job, not this one's). Fails if any control shows the blamed component working while the bug still occurs elsewhere (e.g. the same input parses fine without the flag, the "missing" module prints in the same build, the operator already behaves correctly outside the condition), if the evidence shows the damage happens before the code the plan blames ever runs, or if the plan adopts a cause from the thread that the package's own measurements contradict. A plan whose cause matches the issue's or a maintainer's diagnosis passes only if the repro evidence does not contradict it | required |
| Scope is one bounded change | The plan's change list, in-scope and not-in-scope statements, and files, read against what the issue actually asks for | The plan makes the one change the issue and repro evidence call for, plus only what that change needs (its regression test, the sibling instance of the same defect in the same code, a note in the PR). Fails if the plan bundles work the issue never asked for: dependency migrations or upgrades, new options or settings, UI rework, redesigns or rewrites of the surrounding subsystem, unrelated "while in the area" fixes, or cross-module unification. A correct core fix wrapped in that extra work still fails. Explicitly deferring related work, or scoping down to the part the student can test and saying so, passes | required |
| A stranger could start executing it | The plan's files/areas and approach | The plan names where the change goes (files, or a specific module/function area) and commits to one chosen approach, so someone else could begin work without asking the author anything. Pinning exact function names during the build is fine when the area and approach are already decided. Fails if the deciding choices are left open: the layer or component is unknown ("gocui? tcell? not sure"), the fix site is "somewhere", the approach is "upstream or vendored, whichever is easier", or the plan is investigate/profile-then-optimize with no chosen change | required |
| Test plan names an observable outcome | The plan's test plan, read against the repro evidence's steps and artifacts | The test plan names a specific observable result that would show THIS fix worked: a command or fixture from the repro re-run with a stated expected output, exit code, measurement, or visible behavior, and ideally the controls re-run unchanged. Fails if the only test is subjective ("should feel fast", "should work", "nothing else should feel broken") or generic ("run the full test suite and make sure nothing regresses") with no fix-specific observable | required |
| Unknowns stated, not dressed as certainty | The plan's diagnosis, risk/unknowns notes, and the plan comment's certainty language, read against the repro evidence | The plan's confidence matches its evidence: anything not yet verified is stated as an open question or risk rather than asserted. Fails if the plan or comment presents as settled something the package itself leaves open or contradicts (e.g. calling a version difference "a red herring" while the repro shows the version flips the outcome, or claiming a root cause is confirmed without evidence that shows it) | required |
| Comment engages the thread's direction | The plan comment and plan, read against the thread highlights' maintainer/owner/collaborator comments and any open or prior-art PRs named there | When a maintainer has given explicit direction in the thread (isolated the culprit code, posted a patch or test build, chosen among fix options, or said how it should be done), the plan follows that direction or the comment explicitly addresses it and explains the departure. When the thread names an open or prior-art PR for this issue, the comment acknowledges it. Fails if the comment ignores explicit maintainer direction (e.g. a docs-only workaround plan when the owner has already pointed at the code and posted a patch for testing). Passes trivially when the thread has no maintainer direction and no PRs | required |
| AI-use disclosed where the policy requires it | The repo-facts "contribution policy" line, and the plan comment for a disclosure statement | Fails only when the policy affirmatively instructs disclosing AI assistance on issue comments or all contributions "in any form" (naming the tool and extent) and the plan comment contains no disclosure. Passes when the policy is silent, when it only asks contributors to understand/take responsibility for code, when it asks for human-voiced comments without a separate disclosure ask, when disclosure is scoped to pull requests only, or when the required disclosure is present. Every package is treated as AI-assisted work | required |

## Verdict rule

Accept (ready to post and build from) only if all seven required checks
pass. Reject (hold) if any required check fails. An `unclear` grade
counts as a fail: a plan that cannot be verified from its own package
is not ready to build from. There are no preferred checks: each family
here is a reason a plan should not go up, not a reason to rank it lower.
