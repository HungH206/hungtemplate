# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded | The repro report's environment line, read against the dimensions the issue itself calls essential (see `references/evidence-guide.md`, "Environment") | An environment record is present, and it names every dimension the issue treats as load-bearing to the trigger (the tool version, OS, and any issue-specific dimension such as a dependency version, browser language order, build profile, or driver). Fails if there is no environment record at all, or if it omits a dimension the issue explicitly calls necessary | required |
| Steps are followable by a stranger | The repro report's steps, commands, files, and config | A stranger with no access to the student's machine or accounts could carry out the same steps from a stated starting point, using only what the report gives directly. Fails if the steps point at resources nobody else can reach (a private repo, an unshared config), or if they omit a condition the issue names as necessary to reach the bug (a required flag, driver, or input shape), even when what is given is otherwise concrete | required |
| Artifact shows the issue's behavior | The exact trigger used (command, flags, expression, config) and its output, read against the issue's stated trigger and failure signature, and against the repo-facts version info if a different version is used | The trigger executed matches the issue's own construct (same flag syntax, same expression shape, same input structure, not a substituted or simplified stand-in), and the shown artifact exhibits the SAME failure signature the issue reports (same error type, same exit behavior, same observable symptom) — not a different, milder, or unrelated failure narrated as if it were the reported one. A version or environment different from the issue's original report passes only when that difference is named explicitly and the matching behavior is still shown on it. An honest, well-targeted cannot-reproduce (the right trigger attempted, a clear statement of what did not match) also passes: this check grades whether the right thing was attempted and read correctly, not whether the bug appeared | required |
| Outcome is stated honestly | The report's own concluding language and certainty claims, compared against the artifact the same report shows | Every claim of certainty ("confirmed," "verified," "root cause," "100% reproducible," "guaranteed") is backed by an artifact shown in that same report. An honest, hedged cannot-reproduce passes cleanly. Fails when a report asserts confirmation or diagnosis with no artifact behind it, when it substitutes repetition or multiple attempts for an artifact that actually matches ("ran this ten times," "two separate machines"), or when its stated conclusion contradicts what its own shown artifact demonstrates | required |
| Claim comment states a specific, honest intent | The candidate claim comment | The comment names something concrete and particular to this issue (a next investigation step, a file or function, a thread pointer it follows up on), not interchangeable flattery or boilerplate that could be pasted onto any issue, and it does not promise an outcome or timeline it cannot back (no guaranteed fix times, no "100%/guaranteed reproducible" framing carried into the claim). Fails when the comment is generic enough to paste onto any issue unchanged | required |
| AI-use disclosed where the policy requires it | The repo-facts "contribution policy" line, and the candidate claim comment plus repro report for a disclosure statement | Fails only when the policy affirmatively instructs disclosing AI assistance specifically on issue or PR comments (naming the tool and the extent of use) and neither candidate comment discloses it. Passes when the policy is silent, when it only asks contributors to personally understand/test/take responsibility for contributions without a comment-level disclosure ask, when it asks for human-voiced comments without a separate disclosure ask, when disclosure is scoped to pull requests rather than issue comments, or when the required disclosure is present | required |

## Verdict rule

Accept (ready to post) only if all six required checks pass. Reject
(hold) if any required check fails. Treat `unclear` on a required check
as a fail: proof that cannot actually be verified from the package is
not proof that is ready to post upstream. There are no preferred
checks in this rubric — every family the lecture named gates the
verdict directly, since a reproduction package with a real gap in any
one of them is not ready to post, not merely a worse one to rank.
